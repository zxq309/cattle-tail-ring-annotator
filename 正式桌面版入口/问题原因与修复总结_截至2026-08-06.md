## 4. 已修复问题

### 4.1 九轴图中存在多余的行为标签泳道

#### 现象

九轴数据面板除了 11 条传感器数据，还显示“休息、行走、甩尾”等行为标签泳道。这些内容已经在下方标注区域出现，在九轴图区重复显示会占用空间并产生大量空白。

应当保留的 11 条数据为：

- 加速度 X、Y、Z；
- 角速度 X、Y、Z；
- 磁场 X、Y、Z；
- 温度；
- 运动。

#### 原因

绘图组件同时承担两种职责：

1. 绘制传感器曲线；
2. 绘制标注事件泳道。

事件泳道使用固定高度，即使没有标注事件也会持续占用垂直空间。

#### 修复方式

在 `dual_anchor_precision_v2_mixin.py` 中：

- 固定关闭标签泳道；
- 删除“泳道”显示/隐藏按钮；
- 标注事件继续保留在下方事件编辑面板；
- 主曲线面板只显示 11 条传感器数据。

对应提交：`4f0a4df`

#### 结果

九轴主面板全部空间用于传感器曲线，不再出现行为标签造成的多余空白。

### 4.2 温度和运动曲线不显示

#### 现象

打开九轴 JSON 后，加速度、角速度和磁场正常显示，但温度和运动没有可见曲线。

#### 原因

加速度等数据约为 50 Hz，而温度和运动属于低频汇总数据，采样间隔明显更长。

旧绘图逻辑对所有曲线使用相同的数据间隙阈值：

- 高频九轴数据相邻约 20 ms；
- 温度和运动相邻可能是数秒或一分钟；
- 低频数据的相邻点被误判为“数据断点”。

绘制时，每个低频点都只执行路径起点操作，没有连接到下一个点，因此看起来像没有数据。

#### 修复方式

在 `widgets.py` 中：

- 把 `temperature` 和 `motion` 标记为低频序列；
- 根据每条低频序列自身的时间戳计算采样周期；
- 使用“有效采样间隔中位数 × 1.5”作为该序列的断点阈值；
- 高频九轴数据继续使用原有间隙规则。

对应提交：`11e36c4`

#### 结果

温度和运动可以按自身采样周期连续绘制，真实数据断点仍然会正确断开。

### 4.3 字体与背景颜色接近，部分文字看不清

#### 现象

下拉框、弹窗、表格标题、禁用控件等位置出现浅色文字配浅色背景，导致内容难以辨认。

#### 原因

原有 Qt 样式只覆盖了部分主窗口控件，没有完整覆盖：

- `QDialog`；
- `QMessageBox`；
- `QInputDialog`；
- `QProgressDialog`；
- 下拉框弹出列表；
- 菜单；
- 表头；
- 禁用控件；
- 工具提示。

这些控件会继承 Windows 系统主题颜色，在部分系统配色下形成低对比度组合。

#### 修复方式

在 `window_ui.py` 中补全统一样式：

- 普通文字使用深色；
- 输入框和下拉框使用白色背景；
- 禁用控件使用灰蓝背景和可读文字；
- 下拉列表选中项使用蓝底白字；
- 表头、菜单、弹窗和工具提示明确设置前景色和背景色。

### 4.5 导入九轴 JSON 后工具整体变慢，150% 缩放最明显

#### 现象

未打开 JSON 时界面正常；打开一小时九轴 JSON 后，鼠标移动、播放头更新和其他界面操作明显变慢。在 Windows 显示缩放为 150% 时尤其严重。

#### 原因

工具原本会缓存复杂的九轴曲线背景，只在缓存上叠加播放头，避免每次重画所有曲线。

高 DPI 下存在尺寸单位不一致：

- Qt 位图缓存尺寸使用物理像素；
- 窗口尺寸使用逻辑像素；
- 原代码直接比较两者宽高；
- 150% 缩放时两者永远不相等。

因此缓存持续被误判为失效。播放头每移动一次，程序都会重新绘制 11 条、一小时长度的曲线，导致主线程变慢。

#### 修复方式

在 `cached_widgets.py` 中：

- 使用 `deviceIndependentSize()` 比较逻辑尺寸；
- 同时检查缓存和窗口的设备像素比；
- 允许小于 1 像素的浮点误差；
- 缓存有效时只重画播放头和交互覆盖层。

对应提交：`ab129ef`

#### 结果

150% 缩放下曲线缓存可以正常复用，播放头移动不再反复重画所有数据。

### 4.6 切换分段视频时九轴进度回到开头

#### 现象

一个九轴 JSON 约一小时，而视频被分成多个十几分钟的 `hiv00000.mp4`、`hiv00001.mp4` 等文件。

当前 JSON 尚未标注完就需要切换下一段视频。旧逻辑每次切换视频都会把九轴播放头重置到开头，需要人工重新调整九轴位置。

#### 原因

`hiv00001.mp4` 这种文件名不含日期时间，程序无法从文件名识别视频真实起始时间，于是使用默认映射：

```text
视频 0 秒 = JSON 0 秒
```

新视频打开后，播放器首先报告视频时间 0，九轴播放头便被同步回 JSON 开头。

#### 修复方式

在切换视频前保存：

- 当前九轴播放头；
- 当前曲线视窗范围；
- 当前视频路径。

新视频成功打开后：

- 确认它是不同的视频文件；
- 把新视频 0 秒映射到切换前的九轴当前位置；
- 设置对齐方式为 `continuation / 分段续接`；
- 恢复九轴播放头；
- 恢复原曲线缩放范围；
- 清理上一段视频遗留的定位等待状态。

载入工程过程中打开视频不会套用分段续接，避免覆盖工程中保存的对齐信息。

对应提交：`30a952b`

#### 注意事项

分段续接默认认为两段视频连续。如果录像之间存在缺帧或时间间隔，仍应使用：

- ±0.1 秒、±1 秒、±10 秒微调；
- 画面角标；
- “钉住当前帧”。

### 4.7 视频播放完成后无法再次播放

#### 原现象

- 视频播放到结尾后画面定住；
- 再次点击播放按钮没有反应；
- 播放结束后拖动进度条，按钮显示“定位后播放”；
- 等待约 8 秒后按钮恢复“播放”，但再次点击仍没有反应。

#### 根本原因

视频播放完成后，libVLC 进入 `ended` 状态。旧处理只把按钮文字改回“播放”，没有执行以下恢复操作：

- 让播放器退出 `ended`；
- 清除 UI 层等待确认的定位请求；
- 清除媒体引擎层暂存的定位请求；
- 重新建立可播放的媒体状态。

底层安全定位逻辑只会在 `playing` 或 `paused` 状态真正执行定位。`ended` 状态下拖动产生的定位请求只会暂存，因此 UI 会进入“定位后播放”，但播放器始终无法确认新位置。

#### 修复方式

新增独立的 `EndedReplayMixin`，放在正式 v7 窗口调用链最上层，专门管理播放结束后的恢复流程。

播放结束时：

1. 记录媒体已经进入结束状态；
2. 清除九轴/视频配对层的等待状态；
3. 停止定位确认计时器；
4. 清除媒体引擎内部待执行的旧定位；
5. 将按钮和状态提示恢复为可重播状态。

结束后直接点击播放时：

1. 保留当前视频路径和视频—九轴对齐关系；
2. 安全重载同一个视频媒体；
3. 将重播位置设置为视频 0 秒；
4. 同步九轴播放头到该视频起点对应的 JSON 时间；
5. 恢复倍速、音量和静音状态；
6. 启动播放。

结束后先拖动进度条时：

1. 将拖动位置解释为“重播起点”，不再解释为新的时间对齐点；
2. 立即更新视频进度显示和对应的九轴播放头；
3. 点击播放后安全重载媒体；
4. 等播放器重新可定位后，从用户选择的位置播放。

底层 `SafeMediaEngine` 新增：

- `clear_pending_seek()`：清除旧媒体状态遗留的定位请求；
- `replay_from_ms()`：重新打开同一媒体，并在播放器重新可定位后应用指定重播位置。

媒体引擎同时增加只读的 `current_status`，让 UI 能明确区分 `ended`、`paused` 和 `playing`。

对应提交：`8300d21`

### 4.8 标注结束后播放头回跳，事件表显示相对进度时间

#### 原现象

结束一次区间标注后：

- 视频进度自动回到该事件的开始位置；
- 九轴播放头随后也回到事件开始位置；
- 事件表“开始”和“结束”显示 `00:35:32.758` 一类九轴相对进度，而不是传感器记录时间。

#### 播放头回跳的根本原因

事件保存本身是正确的，`t0` 和 `t1` 分别记录了打标开始和结束位置。问题发生在事件表刷新阶段：

1. `_add_event()` 保存新事件，并把它设为当前选中事件；
2. `_refresh_events()` 重建事件表并自动高亮新行；
3. 旧代码在 `selectRow()` 前已经解除表格信号屏蔽；
4. 自动高亮触发了 `itemSelectionChanged`；
5. `_event_selected()` 将程序自动选择误认为用户点击，调用 `set_playhead(t0)`；
6. 视频开始异步定位到事件起点；
7. `_add_event()` 只使用 `seek_video=False` 临时恢复九轴结束位置；
8. 视频定位完成后再次把九轴播放头同步拉回事件起点。

因此数据没有保存错，是“程序自动选中”和“用户手动点击”没有区分造成的界面定位错误。

#### 播放头回跳的修复方式

- 重建事件表和自动高亮新事件时保持信号屏蔽；
- 自动高亮只改变选中行，不触发 `_event_selected()`；
- 结束打标后，视频和九轴继续停留在事件结束位置；
- 用户手动点击事件表中的某一行时，仍然跳转到该事件开始位置；
- 不使用“先跳到开始、再强制跳回结束”的双重视频定位，避免异步定位竞争。

#### 时间显示错误的根本原因

旧事件表直接使用：

```python
format_relative(t0)
format_relative(t1)
```

所以显示的是从九轴 JSON 开头算起的相对进度。

悬浮提示中的“记录时间”使用的是：

```text
JSON createTime + 相对时间
```

因此悬浮提示正确，而事件表显示语义不符合人工查看需求。

#### 时间显示修复方式

事件表改为显示：

```text
开始记录时间 = JSON createTime + t0
结束记录时间 = JSON createTime + t1
```

显示格式统一为北京时间：

```text
YYYY-MM-DD HH:MM:SS.mmm
```

表头改为：

- `开始记录时间`；
- `结束记录时间`；
- `时长`。

“时长”仍显示相对持续时间。点事件的结束位置仍显示“点”。

底层事件数据没有改为绝对时间，仍保存相对毫秒 `t0/t1`，因为九轴样本定位、视频同步、训练样本生成和导出都依赖相对时间。此次修改只改变事件表显示。

对应提交：`e58a426`

### 4.9 钉住后时间轴没有双向联动，微调正负方向相反

#### 原现象

完成“钉住 当前帧=播放头”后：

- 暂停时拖动九轴时间轴，视频没有跟随；
- 暂停时拖动视频进度条，九轴播放头没有跟随；
- 界面又显示“待配对：九轴……↔ 视频……；按播放”；
- `-0.1s/-1s/-10s` 实际让视频前进；
- `+0.1s/+1s/+10s` 实际让视频后退。

#### 钉住计算本身是否正确

钉住使用的偏移计算是正确的：

```text
video_start_wall = data_create_time + data_playhead - video_playhead
```

它能够把当前九轴时刻与当前视频帧映射为同一真实时刻。问题不在钉住结果，而在钉住之后的时间轴交互分支。

#### 双向联动失效的根本原因

旧代码仅根据播放器是否正在播放决定交互模式：

```text
正在播放 → 九轴和视频同步定位
处于暂停 → 九轴、视频分别作为两个独立锚点
```

这套判断没有检查是否已经存在有效对齐。因此即使 `align_method` 已经是 `pin`，暂停后拖动仍会无条件进入独立选点模式，刚建立的时间映射虽然仍保存在工程状态中，但时间轴交互没有使用它。

#### 第一阶段双向联动修复

提交 `03880d0` 首先在 `dual_anchor_precision_v2_mixin.py` 中增加统一的有效对齐判断：

- 必须已经打开九轴和视频；
- 必须存在 `video_start_wall_ms`；
- `none` 和 `default / 零偏移待校准` 仍属于未校准状态；
- `pin`、`filename`、`corner`、`manual`、`continuation` 等有效方式属于已联动状态；
- 载入工程后根据工程中保存的有效对齐恢复联动。

暂停状态下的处理改为：

```text
尚未有效对齐：保留九轴和视频独立选点，用于首次配对
已经有效对齐：拖九轴时定位视频，拖视频时更新九轴
```

钉住、文件名对齐、画面角标、人工微调和分段续接后都会清除旧的待配对锚点，并继续使用已有的安全定位、范围限制和长 GOP 定位确认链。

这一步解决了“已对齐但暂停拖动不联动”，但后续使用发现：仅由 `align_method` 推断状态，无法表达“映射仍然存在、但用户主动解除钉住并要独立校准”这一合法状态；同时，打开新视频或新 JSON 时底层初始化仍会重写播放头和映射。当前最终实现已经改为显式钉住状态和数据源切换事务，详见 4.10。

#### 微调方向相反的根本原因

视频目标位置的计算为：

```text
video_time = data_create_time + data_playhead - video_start_wall
```

旧代码却执行：

```text
video_start_wall += delta
```

因此传入正数时 `video_time` 反而减小，正负按钮显示语义与实际画面移动方向相反。

#### 微调方向修复方式

在 `playback_mixin.py` 中改为：

```text
video_start_wall -= delta
```

现在按钮含义统一为：

- `+`：当前九轴时刻对应的视频位置向前；

- 微调完成后对齐方式记为 `manual`，时间轴继续双向联动。

该修改不改变标注协议、工程 JSON 格式、事件 `t0/t1` 或导出结构。

### 4.10 钉住改为开关，并让双向联动与视频/JSON 续接同时成立

对应提交：`6fb2403`

#### 需求背景

标注过程中存在两种方向相反、但都必须支持的操作：

1. 正式标注时，视频与九轴必须钉住，任意一条时间轴变化都应推动另一条；
2. 对齐或修正时，两条时间轴必须暂时独立，标注员才能分别找到同一真实时刻，再重新钉住。

数据源也会在两个方向续接：

- 九轴 JSON 还没结束，但当前分段视频已经结束，需要打开下一段视频；
- 当前视频还没结束，但当前 JSON 已经结束，需要打开下一份 JSON。

此前只能分别满足其中一部分。保持双向联动后，打开数据源时产生的初始化位置会通过联动链传播到另一条时间轴；阻止这种传播后，正常拖动又无法双向联动。

#### 为什么双向联动和切换续接会互相覆盖

旧实现把三种含义混在同一组变量和回调中：

- `align_method` 表示映射怎样产生；
- `video_start_wall_ms` 表示时间换算关系；
- 播放器是否播放被用来决定当前应当联动还是独立选点。

但“映射存在”和“当前是否允许联动”并不是同一件事。例如用户解除钉住进行人工修正时，旧映射仍应保留用于回退和显示，但当前交互必须独立。仅看 `align_method=pin` 会误判为仍应联动；仅看播放器已暂停又会误判为应重新选点。

此外，打开媒体不是一个瞬时动作。新视频在初始化阶段会依次报告 0 秒、时长、播放、暂停和定位确认等状态。如果这些回调仍按旧映射驱动九轴，九轴会被新视频的 0 秒拉走；如果切换代码刚恢复九轴位置，稍后的媒体回调又可能把恢复结果覆盖。

#### 为什么切换 JSON 会把视频拉回开头

旧调用链依次发生以下操作：

1. `_display_motion_data()` 把新 JSON 播放头设为 0；
2. `ProductionSafetyMixin.open_json()` 清除旧对齐并尝试按视频文件名重新对齐；
3. 海康 `hiv00001.mp4` 一类文件名没有可靠记录时间，只能建立临时零偏移；
4. `_seek_video_to_playhead()` 按“新 JSON 0 秒”定位视频；
5. 视频因此被拉回 0 秒，切换前正在看的画面丢失。

所以问题不只是“没有保存视频进度”，而是新 JSON 初始化、默认映射和自动定位连续覆盖了切换前的位置。

#### 显式钉住状态

在 `dual_anchor_precision_v2_mixin.py` 中增加 `_timelines_linked`，明确区分两种工作模式：

```text
未钉住 / 校准模式
    九轴拖动只改变九轴
    视频拖动、播放和逐帧只改变视频
    微调按钮只改变视频位置

已钉住 / 正式标注模式
    九轴变化会定位视频
    视频变化会更新九轴
    微调会修改正式时间映射
```

`window_ui.py` 把“钉住”按钮改为可选中开关：

- 黄色“钉住 当前帧=播放头”表示未钉住；
- 绿色“✓ 已钉住（点击解除）”表示已钉住；
- 工具提示说明两种模式的用途。

解除钉住时，程序会暂停视频，保存当前九轴位置和视频位置，再进入独立校准。重新钉住时按照当前两个位置重新计算：

```text
video_start_wall
= data_create_time + data_position - video_position
```

如果视频拖动定位仍在等待播放器确认，程序不会用尚未到位的请求位置建立映射，而是保持未钉住并提示等待。画面到位后再次点击即可钉住。

画面角标校准也适配了显式状态：先建立角标映射并打开联动，再用播放器实际当前帧刷新九轴，避免校准期间的独立模式拦截这次必要同步。

#### 为什么未钉住时暂停正式标注和导出

未钉住意味着视频帧与九轴样本的对应关系尚未确认。此时继续创建事件，会让事件边界落在无法证明正确的样本位置；直接导出则可能把错误映射带入训练数据。

因此当前规则为：

- 标签列表和专项标签开关在校准模式下禁用；
- 标签快捷键和底层新增事件入口都进行二次拦截；
- 已有事件仍可查看和编辑；
- 存在尚未结束的标注区间时，阻止解除钉住；
- 导出校验增加结构性错误 `timelines_unlocked`；
- 重新钉住后恢复正式标注和导出。

#### 视频切换事务

打开下一段视频前，程序建立一次切换快照，保存：

- 当前九轴播放头；
- 当前九轴曲线视窗；
- 当前视频位置；
- 原 `video_start_wall_ms` 和 `align_method`；
- 原钉住状态；
- 切换前是否正在播放。

切换开始后会暂停播放，并设置 `_source_switch_active`。在新媒体初始化完成以前：

- 平滑播放头停止推进；
- 媒体时间回调只更新视频侧显示，不推动九轴；
- 普通跨时间轴定位请求被拦截；
- 播放操作会被阻止，钉住和微调控件暂时禁用。

新视频成功打开后建立：

```text
新视频 0 秒 = 切换前九轴播放头
video_start_wall = data_create_time + preserved_data_position
align_method = continuation
```

媒体完成初始化和必要的 0 秒定位后，程序才解除冻结，恢复九轴播放头和原曲线视窗。原来已钉住则继续联动，原来未钉住则继续保持校准模式。文件选择被取消或打开阶段失败时，使用快照恢复原映射、位置、钉住状态和原播放状态。

#### JSON 切换事务

打开下一份 JSON 前同样保存视频位置和原界面状态。切换期间先拦截旧 `_seek_video_to_playhead()`，防止新 JSON 的 0 秒通过临时映射把视频拉回开头。

新 JSON 成功载入后建立：

```text
新 JSON 播放头 = 0
视频位置 = 切换前视频位置
video_start_wall = new_data_create_time - preserved_video_position
align_method = data_continuation
```

九轴曲线视窗按以下规则恢复：

- 原来显示全部数据，新 JSON 仍显示全部；
- 原来使用局部时间尺度，新 JSON 从 0 秒开始保留相同视窗跨度。

原钉住状态继续保留。切换前已钉住时，新 JSON 0 秒与当前视频帧建立正式联动；切换前未钉住时，两个位置保留但仍处于独立校准模式。

#### 工程保存和 v4 兼容

工程格式版本继续为 v4，没有升级协议，也没有改变事件、标签或导出结构。只在现有对象中增加可选状态：

```text
align.locked       当前是否钉住
ui.timelinesLinked 与 align.locked 对应的界面恢复字段
ui.dataAnchorMs    未钉住时的九轴位置
ui.videoAnchorMs   未钉住时的视频位置
```

载入顺序为：

1. 优先读取 `align.locked`；
2. 没有时读取 `ui.timelinesLinked`；
3. 旧工程两个字段都没有时，根据原 `align_method` 和映射是否有效推断。

因此旧 v4 工程仍可载入；新工程保存为未钉住时，重新打开会恢复两个独立位置；保存为已钉住时，重新打开会恢复映射并执行同步定位。

#### 正式生产代码修改位置

- `dual_anchor_precision_v2_mixin.py`：显式钉住状态、两种交互模式、视频/JSON 切换事务、工程状态保存恢复、标注和导出保护；
- `window_ui.py`：钉住按钮改为开关并增加状态说明；
- `ended_replay_mixin.py`：视频结束后的重播位置只有在已钉住时才允许推动九轴；
- `playback_mixin.py`：增加 `data_continuation / JSON 续接` 的对齐状态名称。

该修改不改变标注协议 v2、工程格式 v4、事件 `t0/t1`、`reviewed_range`、已有标签或训练导出列。

### 4.11 点击播放后重复前几帧，时间和九轴进度停住后跳变

对应正式代码提交：`eda3f0c`

#### 用户看到的两个独立现象

1. 视频已经停在某个位置，点击播放后，当前位置附近的前几帧会反复播放一段时间，之后才真正向后播放；
2. 视频画面播放流畅，但右侧视频时间和进度条会停住，再突然跳到画面当前时间；已钉住的九轴播放头也会一起停住和跳变。

第二个现象不是画面解码卡顿。视频画面使用逐帧时间戳输出，而界面原来直接依赖 libVLC 对外公开的粗粒度播放时间，两者更新频率不同。

#### 重复前几帧的直接原因

普通暂停后继续播放时，`PlaybackMixin.toggle_play()` 仍然调用 `_seek_video_to_playhead()`。这会把“继续播放”误当成一次新的长 GOP 定位，并建立最长8秒的定位确认状态。

正式调用链中同时存在两处重试：

- `SeekConfirmationMixin._on_media_time()` 在定位未确认时每约400 ms再次发送目标位置；
- `SeekWatchdogMixin._check_pending_seek()` 即使VLC没有产生新的时间信号，也每约400 ms再次发送同一位置。

在 `hiv00002.mp4` 的 `00:04:07.767` 位置实测，点击播放后出现：

```text
set_time_ms(247767)
约每 400～422 ms 再执行一次
连续约 20 次
直到 8 秒定位确认超时
```

每次调用都会让长 GOP 解码重新从定位点附近开始，所以刚播放出去的几帧又被拉回。8秒后待确认状态清除，视频才继续向后。这是程序重复定位造成的确定性问题，不是原视频PTS跳变；H.265和约4.8秒关键帧间隔只会放大视觉表现。

#### 时间和进度条停住后跳变的直接原因

该视频帧率为12.5 fps，每帧PTS约79～80 ms，原始视频时间戳连续。但 libVLC 的 `get_time()` 并不逐帧更新，实测相邻公开时间变化约264～1082 ms，最长更新时间间隔可到约1.25秒；从任意位置刚开始播放时，公开时间和媒体统计还可能更久才批量刷新。

旧平滑逻辑虽然每30 ms刷新一次界面，但 `DualAnchorPrecisionV2Mixin` 又规定显示时间最多只能领先最近一次VLC公开时间400 ms：

```text
VLC 时间暂时不更新
→ 界面最多前进 400 ms
→ 达到上限后冻结
→ VLC 返回下一批时间
→ 界面直接重新锚定并跳变
```

在10×时，这个400 ms是“媒体时间”而不是现实时间，因此只播放约40 ms就会达到上限，问题更明显。九轴播放头使用同一视频时间换算，所以会与视频进度一起停住和跳变。

还确认了一个启动顺序问题：`MediaEngine.poll()` 先发送 `time_changed`，再发送 `playing_changed`。高倍速开始播放时，如果把第一个粗粒度时间直接作为新锚点，会在按钮刚按下时产生一次较大的时间跳变。

#### 正式代码如何修改

`playback_mixin.py`：

- 普通暂停后继续播放不再调用 `_seek_video_to_playhead()`；
- 只有播放头超出视频—九轴共同覆盖范围时，才定位到共同范围起点；
- 拖动、校准、续接、重播等真正改变位置的入口仍保留原定位行为。

`seek_confirmation_mixin.py`：

- 定位请求建立后只发送一次；
- 删除媒体时间回调中的400 ms重复 `set_time_ms()`；
- 未到容差且未超时时只等待确认，不重新启动解码。

`seek_watchdog_mixin.py`：

- 400 ms定时器只读取播放器实际时间并判断“已到位/已超时”；
- 当目标与当前时间已经相同、VLC因数值未变化而没有发送 `time_changed` 时，主动完成确认；
- 超时后恢复播放器实际位置，但不再重新发送定位。

`smooth_playhead_mixin.py`：

- 播放中使用单调时钟每约30 ms连续计算显示视频时间；
- 当前播放速度参与计算，1×、4×、10×分别按对应速率推进；
- VLC公开时间在播放中只保存为校准样本，不再直接更新视频时间、进度条和九轴播放头；
- 校准参考值按“最近VLC时间 + 经过的单调时间 × 播放速度”外推；
- 校准速度限制为额定播放速度的 ±12%，逐步消除误差，避免瞬时跳变；
- 播放器处于播放状态才推进；暂停、显式定位和播放结束时使用真实播放器位置重新建立精确锚点；
- 处理 `time_changed` 早于 `playing_changed` 的启动顺序，开始播放时保留界面已有位置，不使用第一个粗时间强制跳转。

`dual_anchor_precision_v2_mixin.py`：

- 删除固定400 ms媒体时间上限；
- 仍保留“数据源切换期间冻结”和“未钉住时九轴不跟随视频”的既有保护；
- 已钉住时由新的连续视频时钟同步推动九轴播放头。

#### 为什么没有采用“2秒没有VLC时间就判定画面卡住”

实际验证发现，刚从长 GOP 中间位置播放时，VLC公开时间和“已显示帧数”统计都可能批量更新；即使真实画面仍在播放，两者也可能超过2秒没有新值。把它们当作画面是否停止的依据，仍会制造约2秒的假冻结。

最终实现以播放器真实播放/暂停状态控制连续时钟：播放状态持续就连续推进；暂停、结束或定位等待时停止并重新锚定。这与用户实际看到的画面状态一致，也不会把稀疏统计误判为画面停顿。

#### 实际验证结果

使用原问题文件 `D:\Label\7.27\海康\hiv00002.mp4` 验证：

- 从 `00:04:07.767` 播放6秒，播放后的 `set_time_ms()` 调用为0次；
- 同期VLC公开时间只更新3次，但界面时间连续前进约5.97秒；
- 界面采样中的最大停顿约0.109秒，不再出现约1～2秒停住后跳变；
- 1×、4×、10×各播放2秒，播放后定位调用均为0次；
- 三种速度下连续刷新间隔最大约0.032秒；
- 10×中位单次进度约322 ms，符合约30 ms刷新间隔对应约300 ms媒体时间的倍速关系。

该修复不改变标注协议v3、工程格式v4、视频—九轴对齐公式、事件 `t0/t1`、`reviewed_range`、标签或导出结构。

### 4.12 暂停显示目标位置，播放却回到旧位置，九轴随之跳动

对应正式代码提交：`70946de`

#### 录屏确认的现象

录屏 `PixPin_2026-08-10_16-19-05.mp4` 对应实际源文件：

```text
D:\Label\7.29-8.3\海康1\hiv00004.mp4
```

录屏中的位置变化为：

| 状态 | 视频当前位置 |
|---|---:|
| 播放中 | `00:01:07.444` |
| 暂停后 | `00:06:40.173` |
| 再次播放 | `00:01:28.424` |
| 继续播放 | `00:01:35.644` |
| 再次暂停 | `00:06:40.173` |

该文件真实总时长是 `00:18:56.689`，与录屏右侧总时长一致。错误的不是总时长，而是拖动之后“当前播放位置”在旧解码位置与新定位目标之间切换。

#### 根本原因一：待定位请求在旧时间信号之后执行

安全媒体引擎在播放器尚未进入 `playing/paused + seekable` 状态时，会把定位目标暂存在 `_pending_seek_ms`。旧 `poll()` 顺序为：

```text
读取旧播放器时间
→ 向界面发送 time_changed
→ 再执行 _pending_seek_ms
```

因此用户虽然已经把进度条拖到 `00:06:40.173`，点击播放后的第一批回调仍可能把之前的 `00:01:07.444` 发给界面。未钉住时视频进度条直接回到旧位置；已钉住时同一个旧时间还会通过正式映射推动九轴播放头。

暂停时播放器又可能公开已经请求的6分40秒，因此界面看起来在“播放回旧位置、暂停回目标位置”之间反复切换。定位真正生效的时机由VLC解码和长GOP状态决定，所以有时要重复暂停/播放才能恢复。

#### 根本原因二：暂停时使用滞后的VLC公开时间覆盖连续时间

对另一个问题文件 `D:\Label\7.27\海康\hiv00002.mp4` 实测，1×播放6秒后：

```text
连续显示位置：253511 ms
VLC公开时间： 251803 ms
```

画面仍在播放，但VLC时间落后约1.7秒。旧暂停回调无条件用 `get_time_ms()` 覆盖连续显示位置，导致已钉住的九轴在暂停瞬间被一起拉回。

#### 为什么不采用自动FFmpeg无损封装

本次按要求保留原文件直接播放：

- 不自动运行FFmpeg诊断；
- 不生成MKV或其他修复视频；
- 不修改原视频；
- 现有“FFmpeg诊断/无损封装修复”按钮只作为人工备用。

解决重点从“改变文件容器”改为“严格管理定位请求和时间回调所属的播放代次”。

#### 新增定位屏障状态机

新增正式模块 `seek_barrier.py`，每次定位独立经过：

```text
waiting        已收到目标，等待播放器可定位
paused_ready   暂停画面已经到达目标
verifying      开始播放，验证真实解码时间
idle           已确认或已取消
```

每次定位都保存目标、8秒截止时间和确认序号。屏障规则为：

1. 目标到达前，拒绝定位前的旧时间、初始化0秒和上一轮定位时间；
2. 暂停时到达目标，只代表画面可以预览，尚不把旧播放代次视为可信；
3. 点击播放后，在VLC真正进入可定位的播放状态时，只重新应用一次目标；
4. 只有目标附近出现继续向前的时间，才确认新播放代次；
5. 10×下第一批真实时间可能已经越过目标数秒，因此确认窗口会按倍速放宽，但远离目标的旧时间仍被拒绝；
6. 8秒超时后取消本轮屏障并恢复播放器实际位置，不循环重发定位。

#### 正式代码修改

`media_engine.py`：

- 在发送 `time_changed` 前增加 `_accept_time_update()` 过滤钩子；
- 基础媒体引擎默认接受，安全媒体引擎可以拒绝过期时间。

`safe_media_engine.py`：

- 接入 `PlaybackSeekBarrier`；
- 定位请求产生时立即建立新屏障；
- 把待执行定位移动到 `super().poll()` 发送时间信号之前；
- 开始播放时只重新应用一次目标，避免400 ms定位风暴；
- 提供“暂停目标是否到位、播放确认是否仍在等待、确认序号、取消确认”等接口；
- 重播和打开新媒体时清除上一媒体代次的屏障。

`seek_confirmation_mixin.py` 和 `strict_seek_mixin.py`：

- 不再只看固定50 ms或1.5秒数值误差；
- 同时检查该时间是否属于当前定位代次并已经由媒体引擎确认；
- 旧时间即使触发回调也不能提前结束定位状态。

`seek_watchdog_mixin.py`：

- 8秒超时时同时取消UI层和媒体引擎层屏障；
- 不重新发送定位命令。

`smooth_playhead_mixin.py`：

- 播放确认未完成时停止连续外推，避免界面先走、画面仍在旧位置；
- 新定位确认时用确认后的真实时间重新锚定；
- 已钉住的正常播放在暂停时冻结最后连续位置，不再使用滞后VLC时间拉回九轴；
- 未钉住校准、数据源切换和显式定位仍保持独立播放器位置，不错误推动九轴。

## 5. 标注协议 v3 标签重构

- 抬尾；

```text

```


存在两条同时有效的“站立”区间。

- 站立；
- 躺卧；
- 行走；
- 采食；
- 其他；
- 未知。

重复或互斥状态重叠会导致：

- 事件次数重复；
- 持续时间重复；
- 审核范围重复；
- 训练标签语义不明确。

1. 定位到错误提示中的时间；

4. 删除重复或错误记录；
5. 重新标成一条连续区间，或让两条记录首尾相接。

- 回退时间后重复打标；
- 在曲线上拖选了另一条区间；
- 修改已有事件边界；
- 载入本身包含重叠的工程。

可以在添加、拖动或修改事件时立即检查身体状态重叠，并选择：

- 拒绝创建；
- 自动截断旧区间；
- 提示合并；

目前只在导出前集中校验。

## 9. 已讨论但尚未完整实现的能力

### 9.1 时钟漂移校正

当前视频与九轴的时间映射只有一个偏移量：

```text
data_time = video_start_wall + video_time - data_create_time
```

它能修正整体相差多少秒，但不能解决录像时钟和传感器时钟速率不同造成的累计漂移。

例如开始位置完全对齐，但 30 分钟后相差 2 秒，仅调整偏移无法同时保证开头和结尾正确。

完整方案应使用双点或多点校准：

```text
data_time = a × video_time + b
```

- `b` 修正起始偏移；
- `a` 修正时间比例漂移。

如果漂移并不稳定，应使用分段线性映射。当前工具只有单偏移和人工微调，没有实现比例或分段漂移校正。

### 9.2 一个工程内分数组

此前提出“一个工程内分数组”，但当前实际工程结构仍是：

```text
 ├─ 一套 labels
 └─ 一套 events
```

当前没有：

如果该要求仍然有效，它属于尚未落地的功能。

### 9.3 多个分段视频的历史清单

## 11. 海康录像时长不一致与连续时间轴校正（2026-08-11）

### 11.1 现象

同一个录像文件在工具、PotPlayer、Windows 媒体播放器和 VLC 中可能显示完全不同的总时长。

已核对的两个文件：

| 文件 | 工具修复前/FFprobe首尾PTS | PotPlayer | Windows播放器 | VLC原生MPEG-PS解析 | 画面实际时长 |
|---|---:|---:|---:|---:|---:|
| `hiv00001.mp4` | `18:55:22.891` | `01:25:36` | 约`18:55:21` | 约`05:00:15` | 约`01:25:00` |
| `hiv00003.mp4` | `00:18:18.322` | `00:18:43` | 约`00:18:17` | 约`01:28:41` | 约`00:18:18` |

VLC 截图右端可见的 `00:15` 和 `28:41` 只是窄时间显示区露出的末尾字符，不代表完整时长；同一台电脑上的 VLC 原生 MPEG-PS 解析分别返回约 `05:00:15` 和 `01:28:41`。

### 11.2 根本原因

这些文件虽然以 `.mp4` 结尾，实际容器是：

```text
MPEG-PS (MPEG-2 Program Stream)
视频：HEVC/H.265
音频：G.711 A-law（pcm_alaw）
```

它们不是具有标准 `moov` 总时长元数据的普通 MP4。播放器只能根据以下不同来源推算时长：

- MPEG-PS 复用码率；
- 文件大小除以估算码率；
- 视频或音频首尾PTS跨度；
- 帧数和估计帧率；
- 播放器扫描到的最大时间戳。

不同播放器采用的来源不同，所以各自可能得到不同结果。

`hiv00001.mp4` 还存在确定的时间戳污染：

```text
最后一个正常视频PTS：34460.809867 秒
下一视频PTS：          97486.055689 秒
单次跳变：             63025.245822 秒
                       = 17小时30分25.246秒
异常位置：             文件字节 265493612 附近
```

音频轨道在同一位置也发生约17小时30分的跳变。使用首尾PTS计算时，文件总时长因此被扩大到 `18:55:22.891`。

异常跳变后仅剩约1.36秒、17个视频包的孤立尾段。实际验证表明，直接定位到该损坏尾段可能触发 VLC MPEG-PS 解码器异常，因此它不能作为可靠标注内容。

`hiv00003.mp4` 的视频和音频PTS连续，没有异常跳变；其首尾跨度为 `1098.322` 秒，因此正确时长约为 `00:18:18.322`。

### 11.3 正式修复逻辑

新增 `media_timeline.py`，并在正式播放器 `SafeMediaEngine` 中统一接入校正时间轴。

打开真实 MPEG-PS 海康录像时，程序执行以下流程：

1. 继续通过文件头识别真实 MPEG-PS，不相信 `.mp4` 扩展名；
2. 在后台只读调用 FFprobe，读取第一条视频流每个包的 `PTS/DTS`、包持续时间和文件位置；
3. 根据正常帧持续时间建立动态阈值，同时要求向前跳变至少达到5分钟，避免把普通丢帧或短暂录像间隙误判成17小时级时间戳污染；
4. 将确定的异常时间戳空洞切分成多个原始时间段；
5. 对可靠时间段建立连续的工具时间轴；
6. 跳变后的孤立片段不足5秒时，保留其诊断边界，但不把它暴露为可拖动、可标注的有效视频；
7. 正常文件没有异常跳变时，不覆盖播放器原始时长。

整个过程只读取原视频，不执行转码、重新封装或源文件写入，也不会自动触发“FFmpeg诊断/无损封装修复”。

### 11.4 为什么必须双向映射

只把界面右侧总时长改短是不够的。否则会出现：

- 进度条显示正确，但拖动仍定位到错误的原始PTS；
- 视频播放头与九轴播放头再次分离；
- 钉住状态下九轴可能跟随异常的18小时时间；
- 标注开始和结束时间可能使用错误视频位置。

现在工具维护两套内部时间：

```text
工具连续时间  <->  原视频/libVLC时间
```

- `duration_ms()` 返回校正后的有效总时长；
- `get_time_ms()` 把 libVLC 原始时间转换成连续工具时间；
- `set_time_ms()` 把进度条目标从连续工具时间反向转换成原视频时间；
- 定位屏障、连续播放时钟、视频进度条、九轴钉住和标注逻辑继续只调用播放器公开接口，因此自动得到同一套校正时间。

### 11.5 索引缓存与切换安全

时间戳扫描结果保存在工具自己的系统缓存目录 `video-timeline` 中，不写入视频所在文件夹。

缓存键包含：

- 视频绝对路径；
- 文件大小；
- 文件最后修改时间。

同一文件再次打开时直接读取缓存。只要视频被替换、修改或大小发生变化，旧缓存就自动失效并重新扫描。

每次切换视频都会增加扫描代次。旧视频尚未结束的后台扫描即使稍后返回，也会因为路径或代次不匹配而被丢弃，不会把上一段视频的校正时长套到新视频上。

后台扫描通过互斥锁串行执行。快速连续切换多个视频时不会同时启动多个 FFprobe 争抢磁盘和CPU；等待中的旧任务发现代次已失效后会直接退出。
